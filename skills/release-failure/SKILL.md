# Failed release

A `CreateRelease` run publishes in this order: tag, changelog on `master`, GitHub Release, TGZ/RPM/DEB packages, Docker images, and last the version bump on the release branch. A failure after the tag leaves the release published without its bump, and every later scheduled run for that line fails with `release line X.Y.Z already has a release tag`. So a failure after the tag blocks the line until a recovery run passes.

The issue is https://github.com/ClickHouse/clickhouse-private/issues/78182. The active `gh` account can be one without access to the private repository; prefix every `gh` call on it with `GH_TOKEN=$(gh auth token --user leshikus)`. Do not switch the active account.

## 1. Find the cause

```bash
mkdir -p ~/tmp/run<id> && cd ~/tmp/run<id>
gh run view <id> --repo ClickHouse/ClickHouse --log-failed | sed -E 's/^[^\t]*\t[^\t]*\t[^ ]+ //' > c.log
grep -nE "Start execution for|New release:|Failures:|^\[.{19}\]   Fail \[|ERROR" c.log | cut -c1-220
```

- The release tag is in `New release: v...`; the dispatched ref is in `--ref <sha> --release-type`.
- The failed step is the `Fail [<step>]` line under `Failures: N/M`. Read the lines after it for the real error; the job keeps only the tail of a Docker build log.
- `ERROR: command failed after 1/1 attempt(s)` after `lsof +D` in `Export Debian Packages`, and the RPM test's `Signing key not found`, appear in successful runs too. They are not the cause.
- What was published: every step before the failed one that ran. Check the bump: `gh api 'repos/ClickHouse/ClickHouse/contents/cmake/autogenerated_versions.txt?ref=<branch>' --jq .content | base64 -d | grep VERSION_DESCRIBE`. Still the tag's `X.Y.Z.1` means the bump is missing.
- Check that nobody processed it: search the issue comments for the run id, and the later `CreateRelease` runs (`gh run list --repo ClickHouse/ClickHouse --workflow create_release.yml --limit 10`) for one dispatched with `--ref <tag>`.

Compare the cause with the causes already in the issue (body table and each comment's table). When it repeats an earlier one, say so in the comment and name the earlier run.

## 2. Record it in the issue

Post a new comment in the form the earlier comments use:

```markdown
One more major failure:

| Branch | Run | Date | Release | Cause |
|---|---|---|---|---|
| `X.Y` | [<id>](https://github.com/ClickHouse/ClickHouse/actions/runs/<id>) | MM-DD | `vX.Y.Z.N-lts` | <Short name>: <what failed and why>; <what was not published>; version bump missing |

```
<the few log lines that prove the cause>
```

<One paragraph: what was published, which step failed, the bump state and what it blocks. One paragraph on the mechanism, if not obvious.>

Recovery: dispatch `CreateRelease` with `ref=<tag>` and `skip-repo=true`.
```

```bash
GH_TOKEN=$(gh auth token --user leshikus) gh issue comment 78182 --repo ClickHouse/clickhouse-private --body-file ~/tmp/run<id>/comment.md
```

Keep `comment.md`; step 4 appends to it. Write in the style of `technical-language.md`.

## 3. Dispatch the recovery

- **Tag pushed** (the usual case): `ref` is the release tag, never the commit. With the commit, the run stops with `Refusing out-of-order release` or `already has a release tag`.
- **Packages published** (all of `Export/Test TGZ/RPM/Debian Packages` passed): add `skip-repo=true`.
- **Docker images published, only the bump missing**: add `skip-docker=true` too.
- **Tag not pushed** (failure before `Push Git Tag for the Release`): nothing is published and the line is not blocked. Dispatch with `ref=<sha>` and no skips, or leave it to the next scheduled `AutoReleases`.

```bash
gh workflow run create_release.yml --repo ClickHouse/ClickHouse --ref master -f ref=<tag> -f skip-repo=true
gh run list --repo ClickHouse/ClickHouse --workflow create_release.yml --limit 1 --json url --jq '.[0].url'
```

Report the run URL. Wait in the background, not by polling:

```bash
gh run watch <new-id> --repo ClickHouse/ClickHouse --exit-status --interval 60 >/dev/null 2>&1; gh run view <new-id> --repo ClickHouse/ClickHouse | head -20
```

## 4. Add the recovery note

When the recovery passes, verify before you write the note:

- The bump landed: `VERSION_DESCRIBE` on the branch is the next patch, `X.Y.(Z+1).1`.
- The images exist, for each of `clickhouse-server` and `clickhouse-keeper` and each variant the tag ships (`""`, `-alpine`, `-distroless`): `curl -s https://hub.docker.com/v2/repositories/clickhouse/<image>/tags/<X.Y.Z.N><variant> | jq -r '.name // "missing"'`.

Then append the note to the comment from step 2:

```bash
printf '\nRecovered by [<new-id>](https://github.com/ClickHouse/ClickHouse/actions/runs/<new-id>).\n' >> ~/tmp/run<id>/comment.md
GH_TOKEN=$(gh auth token --user leshikus) gh api -X PATCH repos/ClickHouse/clickhouse-private/issues/comments/<comment-id> -F body=@$HOME/tmp/run<id>/comment.md --jq .html_url
```

When the recovery fails, go back to step 1 for the new run, and append `Recovery attempt [<new-id>](...) failed: <cause>.` to the same comment instead.
